### Вывод по RBAC
**CRITICAL**: Ни один компонент справочников не проверяет права доступа. Кнопки «Добавить», редактирования и удаления видны всем ролям. Методы `saveDirItem`/`deleteDirItem` принимают `role` как параметр для лога, но **не проверяют его**. Любой пользователь с доступом к разделу может создавать, редактировать и удалять записи.

## 4. Найденные проблемы

### 🔴 CRITICAL

#### DICT-001 — Отсутствие проверки прав на запись в справочниках
- **Severity**: Critical
- **Справочник**: Все справочники (DirectoriesModule, Currency/Ferry/Checkpoint/Distance)
- **Роль**: Любая
- **Шаги**: Открыть любой справочник → увидеть кнопки Добавить/Изменить/Удалить
- **Факт**: Кнопки действий видны всем пользователям; API `saveDirItem`/`deleteDirItem` не проверяет право на запись
- **Ожидание**: Кнопки должны быть скрыты для ролей без права `settings:write`; API должен отклонять запросы от неправомочных ролей
- **Влияние**: Любой диспетчер/accountant/viewer может модифицировать справочные данные
- **Код**: `firebase.ts` методы `saveDirItem` и `deleteDirItem` — нет проверки permissions
- **Рекомендация**: Добавить `resolvePermission(user, 'settings')` перед операциями записи

#### DICT-002 — Отсутствие XSS-защиты при отображении данных справочников
- **Severity**: Critical
- **Справочник**: DirectoriesModule — все справочники
- **Роль**: Любая
- **Шаги**: Создать запись с названием `<script>alert(1)</script>` → отобразить в списке
- **Факт**: Данные вставляются через JSX `{it[tab.nameField]}`, React экранирует XSS в дефолтном рендеринге, но атрибуты `className` и другие могут быть уязвимы
- **Ожидание**: Все строковые данные должны проходить через экранирование
- **Влияние**: Stored XSS в случае ошибки экранирования
- **Рекомендация**: Явно проверять и экранировать вводимые данные на уровне API
- **Статус**: Open (необходимо тестирование с реальным вводом скриптов)

#### DICT-003 — IDOR: отсутствие проверки принадлежности записи
- **Severity**: Critical
- **Справочник**: Все справочники
- **Роль**: Любая
- **Факт**: Нет фильтрации записей по подразделению, компании или ответственному. Любой пользователь видит все записи всех подразделений. `directoryService.get*` возвращает всю коллекцию.
- **Ожидание**: При необходимости должна быть изоляция по филиалам
- **Влияние**: Утечка данных между подразделениями
- **Статус**: Open (если подразделения не требуются — пропустить)

## 6. Риски

### Критические риски

1. **Обход прав доступа (CRITICAL)**: Любой пользователь с доступом к разделу «Справочники» может создавать, изменять и удалять записи. Нет проверки прав на уровне API.
2. **Повреждение связанных данных**: При удалении записи справочника, которая используется в других разделах (например, направление в плане дохода), данные в этих разделах не проверяются и «тихо» ломаются.
3. **Дубликаты в справочниках**: Нет проверки уникальности, что ведёт к дублированию записей и путанице в выпадающих списках.
4. **Отсутствие пагинации**: При разрастании справочников (1000+ записей) производительность упадёт.

### Риски логистических процессов

- **Расстояния**: Невалидные данные (0 км, отрицательные) попадают в расчёты маршрутов
- **Направления**: Изменение/удаление может сломать планы доходов
- **Группы ставок**: Изменение ставки задним числом может исказить исторические данные
