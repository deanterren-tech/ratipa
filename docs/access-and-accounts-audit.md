# Аудит раздела «Доступ и учётные записи»

Дата: 2 октября 2026. Раздел: «Администрирование» → «Доступ и учётные записи»
(`src/components/modules/UserManagementBlock.tsx`).

## Как сейчас устроено

- **Данные.** Пользователи живут в `users_list/{uid}` (RTDB): `name`, `firstName`,
  `lastName`, `role`, `password` (открытым текстом), `permissions`,
  `customPermissions`, `bazaFieldPermissions`, `isDispatcher`, `viewModes`,
  `onboarding`, `accentColor`, `color`, `lastActive`.
- **Права.** `resolvePermission` (`src/utils/permissions.ts`):
  `customPermissions[key]` → `permissions[key]` → `settings.rolePermissions[role][key]`
  → `DEFAULT_ROLE_PERMS[role][key]`. Значения: `none` / `read` / `write`.
- **Роли.** `root_admin`, `admin`, `dispatcher`, `manager`, `mechanic` + права роли
  в `appSettings.rolePermissions`.
- **Сессии.** Живое применение прав: подписка `App.tsx` на `users_list` + гейт
  `AppShell` (403 без перезагрузки). Принудительный выход — `globalSessionVersion`
  (инкремент завершает все сессии). Присутствие — `ratipapresence/{uid}` (heartbeat).
- **История.** `dbService.logAction` → `auditLogs` (в блоке показывается по сотруднику).

## Найденные проблемы

### Логика (исправлено)

1. **Права роли размножались по сотрудникам.** `handleRolePermChange` писала значение
   в `permissions` и `customPermissions` КАЖДОГО сотрудника роли. Поскольку
   `resolvePermission` читает личные поля раньше роли, после первой же правки роли
   её дальнейшие изменения переставали применяться: у людей оставались «личные» копии.
   → Права роли больше не раскладываются по людям, а **устаревшие копии снимаются**
   (только там, где нет личного переопределения в `customPermissions`) с записью в журнал.
2. **Роль мог выдать себе любой администратор.** Проверка запрещала лишь самопонижение,
   но не назначение `root_admin` — администратор мог повысить себя до разработчика.
   → Трогать учётную запись root и назначать эту роль теперь может только root.
3. **Удаление root** уже блокировалось в интерфейсе (и последнего админа тоже), но
   **в журнал не попадало** → добавлена запись.
4. **Смена роли не писалась в журнал** → добавлена (с прежним и новым значением).
5. **Пароль показывался в поле** с кнопкой «Показать», а диалог смены подставлял
   текущий пароль в поле ввода. → Пароль больше не отображается: только «Пароль задан /
   не задан» и кнопка «Сменить пароль» (пустое поле, подтверждение, запись в журнал).
6. **Рискованные действия без подтверждения** (роль сотрудника, право роли, смена
   пароля) → добавлены понятные подтверждения с последствиями.
7. **Множественное дублирование:** личное переопределение писалось сразу в
   `customPermissions` и `permissions` (два места для одного значения).

### Безопасность (требует решения, не исправлено автоматически)

8. **База открыта для анонимных клиентов.** Приложение входит анонимно
   (`ensureAuth`), а правила в базе это допускают: проверено — `users_list.json`
   и `/.json` читаются и пишутся без авторизации. Значит **любой клиент может
   переписать себе `role`, `permissions` или пароль**. Все проверки прав живут в
   клиенте и держатся только на доверии к клиенту.
   - Файл `database.rules.json` в репозитории **не соответствует данным**: правила
     ссылаются на узел `users`, а приложение пишет в `users_list`, и он не описывает
     большинство узлов. Применять его как есть нельзя — это сломает запись.
9. **Пароли хранятся открытым текстом** (нужны для текущей схемы входа и для
   служебного узла старых страниц `ratipa_home_users`).
10. **Уровень Firebase не проверяет права** — ни `read`, ни `write` по ролям.

### Миграция (предложение, выполнять только по решению)

Чтобы права проверялись на уровне базы без перелома приложения:

1. Вход по **custom token**: сервер (`server.ts`, ключ `firebaseAdmin.ts`) выдаёт
   токен с `uid` пользователя; клиент делает `signInWithCustomToken`.
2. Правила RTDB строятся на `auth.uid` и `users_list/{uid}/role|permissions`:
   чтение — по модулям и правам, запись `users_list` — только root (и своя запись
   для личных настроек), `auditLogs` — запись всем, изменение — никому.
3. Пароли — в хэш (bcrypt/argon2) с постепенным переводом при входе; служебный узел
   `ratipa_home_users` используется старыми страницами — переводить отдельно.

Порядок: сначала токены и проверка в клиенте, потом правила в тестовой базе
(`ratipa-staging`), затем на основной. Обратная совместимость: при отсутствии токена
поведение сохраняется, правила включаются последним шагом.

## Что проверено после правок

- Вкладка открывается, список сотрудников, поиск и роли на месте.
- Пароль в интерфейсе не отображается (`Пароль задан` + «Сменить пароль»).
- У карточки root для администратора выбор роли отключён; обработчики дополнительно
  блокируют правку роли, прав и пароля root не-root пользователем.
- Защита «портал не остаётся без разработчика»: обработчик роли + проверка в
  `dbService.saveUser` (уровень данных), срабатывает при единственном root.
- `tsc` и сборка чистые; данные сотрудников не менялись (11 записей).

## Осталось / требует решения

- Хэшировать пароли.
- Управление сессиями внутри вкладки: сейчас активные сессии — отдельный блок
  «Пользователи и Сессии», история — журнал ниже; при желании объединить.
