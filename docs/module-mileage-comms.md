# Модуль «Пробег и связь» — настройка и запуск сбора (Этап 1)

Раздел «Пробег и связь» показывает состояние телеметрии Nav.by по автопарку:
какие машины давно не давали данных, контекст въезда в РФ, обращения в
поддержку. **Исходные данные для раздела собирает серверный поллер** — браузер
к Nav.by не обращается и токенов не видит.

## Что должен добавить администратор

Секреты задаются ТОЛЬКО в переменных окружения сервера (`.env.local` либо
переменные окружения процесса); они не попадают в браузер и в клиентскую базу.

| Переменная | Обязательность | Назначение |
|---|---|---|
| `NAVBY_LOGIN` + `NAVBY_PASSWORD` | да (или `NAVBY_TOKEN`) | доступ к API nav.by; токен получается автоматически `get-token` и кешируется в процессе |
| `NAVBY_TOKEN` | альтернатива | готовый Bearer-токен (если аккаунт выдаёт его отдельно) |
| `NAVBY_BASE` | нет | хост API, по умолчанию `https://nav.by` |
| `FIREBASE_SERVICE_ACCOUNT` | да (или `_PATH`) | JSON сервисного аккаунта Firebase (запись поллера в RTDB в обход клиентских правил) |
| `FIREBASE_SERVICE_ACCOUNT_PATH` | альтернатива | путь к JSON-файлу сервисного аккаунта (удобно локально) |
| `NAVBY_POLLER_ENABLED=1` | нет | запускать цикл сбора внутри `server.ts` (иначе только через скрипт/крон) |

Серверные файлы `.env.local` и `.env` подхватываются автоматически
(`server/navby/env.ts`, а также `firebaseAdmin.ts`).

## Запуск сбора

```bash
npm run navby:poll                 # один цикл сбора (то, что запускает крон)
npm run navby:poller               # длительный процесс: цикл по интервалу из настроек
npm run navby:poll -- --dry-run    # только чтение Nav.by, без записи в базу
npm run navby:poll -- --prefix test # изолированные ветки test/telemetry_* (проверки)
```

Интервал опроса, порог «нет обновлений», окно ожидания после въезда в РФ,
срок хранения истории, получатели уведомлений — настраиваются в интерфейсе:
раздел «Пробег и связь» → «Настройки» → «Параметры сбора» (право
«Управление интеграцией»). Изменения применяются без перезапуска.

## Планирование регулярного запуска (без деплоя)

**Вариант 1 — один процесс на сервере (рекомендуется для этой машины):**

```bash
cd /Users/sergei/ratipa-fresh-rewrite && npm run navby:poller
```

Держите процесс запущенным (launchd/`nohup`/tmux). Интервал он перечитывает из
настроек после каждого цикла.

**Вариант 2 — Hermes cron (один цикл по расписанию):**

```
/cron add "Пробег и связь: сбор телеметрии" "*/10 * * * *" \
  cd /Users/sergei/ratipa-fresh-rewrite && npm run navby:poll
```

(точный синтаксис — см. `hermes cron --help`; задача запускает один цикл, а не демон).

**Вариант 3 — launchd (macOS):** по образцу `~/Library/LaunchAgents/com.ratipa.server3000.plist`:
`StartInterval` = 600, `ProgramArguments` = `bash -lc "cd /Users/sergei/ratipa-fresh-rewrite && npm run navby:poll"`,
переменные окружения с секретами — в `EnvironmentVariables` либо через `.env.local`.

**Вариант 4 — server.ts:** поставьте `NAVBY_POLLER_ENABLED=1` в окружение сервера —
поллер сам стартует вместе с `npm run dev` / `npm start` и ходит каждые
`telemetry_config.intervalSec` секунд.

**Vercel cron:** требует отдельной serverless-функции в `api/` (например,
/src-обёртки над `runPollCycle`) и деплоя — в текущем этапе НЕ настроено
(деплой не выполнялся). Если планировать в Vercel — добавьте функцию и запись
`crons` в `vercel.json` с заголовком-секретом, чтобы эндпоинт не был публичным.

## Что делает цикл

1. Один батч-запрос `vehicle-list` + один `current-position` (все объекты сразу) —
   при лимите аккаунта 100 req/min это 2 запроса за цикл; наш собственный предел —
   40 req/min с запасом для других интеграций аккаунта.
2. Автопривязка машин к объектам Nav.by по ОДНОЗНАЧНОМУ совпадению госномера
   (кириллица↔латиница); неоднозначности уходят в «конфликты» и решаются
   администратором в интерфейсе.
3. Запись `telemetry_current/<carKey>` и `telemetry_history/<carKey>/<день>/<время>`
   (повторная метка времени из API новым измерением не считается).
4. Закрытие/создание уведомлений (колокольчик портала) с дедупликацией по событию
   и ограничением частоты; при истечении срока хранения — чистка истории.
5. Статус — в `telemetry_integration` (виден в разделе), при недоступности API
   последние данные не обнуляются.

## Недоступность и ошибки

- 401 → однократное переполучение токена; 403/429/5xx/таймаут — ограниченные
  повторы с паузами; после — режим `degraded` (раздел покажет «Сбор данных
  недоступен» и возраст последних данных).
- Параллельные циклы исключены блокировкой `telemetry_poller/lock` в RTDB.

## Данные в RTDB (и правила)

Ветки: `telemetry_config`, `telemetry_integration`, `telemetry_current`,
`telemetry_history`, `telemetry_mapping`, `telemetry_mapping_history`,
`telemetry_navby_objects`, `telemetry_rf_entry`, `telemetry_requests`,
`telemetry_alerts`, `telemetry_poller`.

В `database.rules.json` добавлены правила записи для интерактивных веток
(конфиг/привязки/въезд/обращения — по ролям). **Перед продакшеном правила нужно
применить и сверить с фактически задеплоенными** — поллер пишет через admin SDK
в обход правил, а браузерные записи (привязка, въезд РФ, обращения) зависят от
задеплоенных правил.

## Подтверждённые поля API (живое чтение 10.10.2026)

- `vehicle-list`: `object_id`, `object_uid` (IMEI), `name`, `auto_number`,
  `garage_number`, `status` («1» активен / «0» приостановлен); 78 объектов одним запросом.
- `current-position`: координаты/скорость/`sattelite`/`zazh`/`gsm_lev` + адрес (при
  `get_address=true`), `odom_can`/`odom_virt` (при `get_odometer=true`); 65 объектов
  с позицией одним запросом.
- `datetime` — в поясе +03 (Минск), `datetime_unix` — UTC-эпоха (сверено).
- Времени измерения одометра и отдельного времени сообщения устройства в API НЕТ —
  интерфейс это честно помечает («недоступно», «время измерения — нет в API»).
