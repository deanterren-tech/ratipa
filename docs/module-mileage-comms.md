# Модуль «Пробег и связь» — настройка и запуск сбора (Этап 1)

Раздел «Пробег и связь» показывает состояние телеметрии Nav.by по автопарку:
какие машины давно не давали данных, контекст въезда в РФ, обращения в
поддержку. **Исходные данные для раздела собирает серверный поллер** — браузер
к Nav.by не обращается и токенов не видит.

## Что должен добавить администратор

Секреты задаются ТОЛЬКО в переменных окружения сервера (`.env.local` либо
переменные окружения процесса); они не попадают в браузер и в клиентскую базу.

| Переменная | Обязательность | Назначение |
|---|---|---|
| `NAVBY_LOGIN` + `NAVBY_PASSWORD` | да (или `NAVBY_TOKEN`) | доступ к API nav.by; токен получается автоматически `get-token` и кешируется в процессе |
| `NAVBY_TOKEN` | альтернатива | готовый Bearer-токен (если аккаунт выдаёт его отдельно) |
| `NAVBY_BASE` | нет | хост API, по умолчанию `https://nav.by` |
| `FIREBASE_SERVICE_ACCOUNT` | да (или `_PATH`) | JSON сервисного аккаунта Firebase (запись поллера в RTDB в обход клиентских правил) |
| `FIREBASE_SERVICE_ACCOUNT_PATH` | альтернатива | путь к JSON-файлу сервисного аккаунта (удобно локально) |
| `NAVBY_POLLER_ENABLED=1` | нет | запускать цикл сбора внутри `server.ts` (иначе только через скрипт/крон) |

Серверные файлы `.env.local` и `.env` подхватываются автоматически
(`server/navby/env.ts`, а также `firebaseAdmin.ts`).

## Запуск сбора

```bash
npm run navby:poll                 # один цикл сбора (то, что запускает крон)
npm run navby:poller               # длительный процесс: цикл по интервалу из настроек
npm run navby:poll -- --dry-run    # только чтение Nav.by, без записи в базу
npm run navby:poll -- --prefix test # изолированные ветки test/telemetry_* (проверки)
```

Интервал опроса, порог «нет обновлений», окно ожидания после въезда в РФ,
срок хранения истории, получатели уведомлений — настраиваются в интерфейсе:
раздел «Пробег и связь» → «Настройки» → «Параметры сбора» (право
«Управление интеграцией»). Изменения применяются без перезапуска.

## Планирование регулярного запуска (без деплоя)

**Вариант 1 — один процесс на сервере (рекомендуется для этой машины):**

```bash
cd /Users/sergei/ratipa-fresh-rewrite && npm run navby:poller
```

Держите процесс запущенным (launchd/`nohup`/tmux). Интервал он перечитывает из
настроек после каждого цикла.

**Вариант 2 — Hermes cron (один цикл по расписанию):**

```
/cron add "Пробег и связь: сбор телеметрии" "*/10 * * * *" \
  cd /Users/sergei/ratipa-fresh-rewrite && npm run navby:poll
```

(точный синтаксис — см. `hermes cron --help`; задача запускает один цикл, а не демон).

**Вариант 3 — launchd (macOS), готовый агент:** `./scripts/install-navby-collect.sh [интервал_сек]` —
устанавливает агент `com.ratipa.navby-collect`, который каждые 5 минут выполняет полный цикл
сбора (снимки + история одометра). Файлы: `deploy/launchd/com.ratipa.navby-collect.plist.template`,
`scripts/uninstall-navby-collect.sh`. Для Linux — `deploy/systemd/ratipa-navby-collect.{service,timer}`.

**Вариант 4 — server.ts:** поставьте `NAVBY_POLLER_ENABLED=1` в окружение сервера —
поллер сам стартует вместе с `npm run dev` / `npm start` и ходит каждые
`telemetry_config.intervalSec` секунд.

**Vercel cron:** требует отдельной serverless-функции в `api/` (например,
/src-обёртки над `runPollCycle`) и деплоя — в текущем этапе НЕ настроено
(деплой не выполнялся). Если планировать в Vercel — добавьте функцию и запись
`crons` в `vercel.json` с заголовком-секретом, чтобы эндпоинт не был публичным.

## Что делает цикл

1. Один батч-запрос `vehicle-list` + один `current-position` (все объекты сразу) —
   при лимите аккаунта 100 req/min это 2 запроса за цикл; наш собственный предел —
   40 req/min с запасом для других интеграций аккаунта.
2. Автопривязка машин к объектам Nav.by по ОДНОЗНАЧНОМУ совпадению госномера
   (кириллица↔латиница); неоднозначности уходят в «конфликты» и решаются
   администратором в интерфейсе.
3. Запись `telemetry_current/<carKey>` и `telemetry_history/<carKey>/<день>/<время>`
   (повторная метка времени из API новым измерением не считается).
4. Закрытие/создание уведомлений (колокольчик портала) с дедупликацией по событию
   и ограничением частоты; при истечении срока хранения — чистка истории.
5. Статус — в `telemetry_integration` (виден в разделе), при недоступности API
   последние данные не обнуляются.

## Недоступность и ошибки

- 401 → однократное переполучение токена; 403/429/5xx/таймаут — ограниченные
  повторы с паузами; после — режим `degraded` (раздел покажет «Сбор данных
  недоступен» и возраст последних данных).
- Параллельные циклы исключены блокировкой `telemetry_poller/lock` в RTDB.

## Данные в RTDB (и правила)

Ветки: `telemetry_config`, `telemetry_integration`, `telemetry_current`,
`telemetry_history`, `telemetry_mapping`, `telemetry_mapping_history`,
`telemetry_navby_objects`, `telemetry_rf_entry`, `telemetry_requests`,
`telemetry_alerts`, `telemetry_poller`.

В `database.rules.json` добавлены правила записи для интерактивных веток
(конфиг/привязки/въезд/обращения — по ролям). **Перед продакшеном правила нужно
применить и сверить с фактически задеплоенными** — поллер пишет через admin SDK
в обход правил, а браузерные записи (привязка, въезд РФ, обращения) зависят от
задеплоенных правил.

## Подтверждённые поля API (живое чтение 10.10.2026)

- `vehicle-list`: `object_id`, `object_uid` (IMEI), `name`, `auto_number`,
  `garage_number`, `status` («1» активен / «0» приостановлен); 78 объектов одним запросом.
- `current-position`: координаты/скорость/`sattelite`/`zazh`/`gsm_lev` + адрес (при
  `get_address=true`), `odom_can`/`odom_virt` (при `get_odometer=true`); 65 объектов
  с позицией одним запросом.
- `datetime` — в поясе +03 (Минск), `datetime_unix` — UTC-эпоха (сверено).
- Времени измерения одометра и отдельного времени сообщения устройства в API НЕТ —
  интерфейс это честно помечает («недоступно», «время измерения — нет в API»).

## Постоянный сбор истории одометра («CAN-пробег»)

Живое чтение 11.10.2026 (подтверждено реальными вызовами): Nav.by ОТДАЁТ
исторические измерения одометра по периодам — это не только текущие снимки.

| Метод (подтверждён живым вызовом) | Что отдаёт | Особенности |
|---|---|---|
| `object-stat-data` (`imei,from,to`) | `odom_start`/`s_odo_dt`, `odom_finish`/`e_odo_dt` — границы окна | `s_odo_dt`/`e_odo_dt` — epoch-СЕКУНДЫ UTC, РЕАЛЬНОЕ время измерения (для окна 06:00–07:00 получены 06:00:30 и 06:58:34, не границы окна). `odom_start/finish` — ЦЕЛЫЕ км (округление источника). Машина без движения в окне → `0/null` (это «нет данных», НЕ «ноль км») |
| `city-or-track` (`can_needed=true`) | `start_odometer`/`end_odometer` сегментов движения (float, км) + их времена | Время — «DD.MM.YYYY HH:MM:SS» (+03). У стоянок (`in_motion=0`) одометра нет. Запрос на 3 месяца отдан целиком (1905 сегментов) |
| `parking-movement-report` | `s_odo_can`/`e_odo_can` на границах интервалов стоянка/движение | Поля `s_odo_dt`/`e_odo_dt` в живом ответе ОТСУТСТВУЮТ (не выдумывать) |
| `get-plan-fact` | — | 403: у учётной записи нет прав. Не используется |
| Глубина истории | Проверено: июнь 2025 (16 месяцев назад) — данные есть | Ограничений по глубине в интерфейсе не заявляем; догружаем чанками ≤ 31 дня |

### Как устроен сбор

- **Один цикл в 5 минут** (`scripts/navby-collect.ts`, либо встроенный поллер
  при `NAVBY_POLLER_ENABLED=1`): 1) снимки `current-position` (существующий цикл),
  2) почасовой съём `object-stat-data` (2 измерения/час/машина с реальными временами,
  расписание — `canSweepMin`), 3) суточная догрузка сегментов `city-or-track` +
  `parking-movement-report` за последние полные дни (`canBackfillDays`, идемпотентно).
- **Без браузера и без рейса**: сбор идёт по всем сопоставленным машинам, независимо
  от портала и от наличия рейса. Рейс/день/период только ВЫБИРАЮТ из истории.
- **Single-flight**: цикл съёма защищён блокировкой `telemetry_poller/can_lock`
  (серверный поллер, launchd-агент и ручные запуски не дублируют запросы).
- **Хранение** — `telemetry_can_history/<carKey>/<YYYYMMDD>/<HHMMSSmmm_тег>`:
  значение (км), время измерения (мс epoch), источник, точность (`km_int` —
  округление источника до км / `km_3dec` — исходный float), время получения
  порталом, object_id/IMEI. Снимки портала здесь НЕ дублируются — проектируются
  из `telemetry_history` при чтении (там нет времени измерения — честная пометка).
- **Дедупликация по идентичности измерения (источник + время)**: повтор того же
  измерения из API — не новая точка; одинаковое значение с новым достоверным
  временем — валидная точка (фиксирует отсутствие изменения); повтор с другим
  значением — уточнение источника (`rAt2`); отсутствующее значение не превращается в ноль.
- **Покрытие и состояние**: `telemetry_can_coverage/<carKey>/<день>` (какие методы
  отработали, сколько точек дали) и `telemetry_can_collect` (последние циклы, частота).
  Четыре различимых состояния в UI: «история ещё не загружена» / «источник не даёт
  историю» / «CAN не менялся, измерения поступали» / «новые измерения не поступали».
- **Догрузка по требованию**: `GET /api/navby/can-backfill?carKey&from&to` (прокси,
  токен Nav.by не покидает сервер) — вызывается из карточки машины; при открытии
  дня без покрытия UI запрашивает её автоматически. Поздние измерения встают на
  место по времени и пересчитывают графики.

### Запуск и расписание

```bash
npm run navby:collect                 # один цикл (то же, что делает launchd)
npm run navby:collect -- --stat-only  # только почасовой съём измерений
npm run navby:collect -- --dry-run    # только чтение Nav.by, без записи
npm run navby:backfill -- --car AP96947 --from 2026-10-05 --to 2026-10-09
npm run navby:backfill -- --all --days 3
./scripts/install-navby-collect.sh [интервал_сек=300]   # launchd-агент (macOS)
./scripts/uninstall-navby-collect.sh
launchctl print gui/$(id -u)/com.ratipa.navby-collect   # статус агента
tail -f ~/.hermes/cache/scratch/navby-collect.log       # лог агента
```

Шаблон launchd — `deploy/launchd/com.ratipa.navby-collect.plist.template`
(плейсхолдеры подставляет install-скрипт). Для Linux-сервера —
`deploy/systemd/ratipa-navby-collect.service` + `.timer` (инструкция внутри файла).
Альтернатива без отдельного агента: `NAVBY_POLLER_ENABLED=1` — цикл живёт внутри
`server.ts` (так настроено на текущей машине; интервал снимков — `intervalSec`).

### Интерфейс

Вкладка «Проверка пробега» → раскрытие машины → блок «История CAN-пробега»:
режимы «День» / «Рейс» / «Период» на ОДНОЙ истории; вид «Абсолютное показание» /
«Прирост от начала периода»; линия + синхронный график приростов (сбросы,
разрывы, приросты на стоянке видны и не скрываются); зум выделением и пресетами
(до часов/минут); подсказка точки — время измерения, значение, предыдущее, прирост,
интервал, качество; полнота (первое/последнее, количество, разрывы, покрытие по
дням, ограничения источника); список «Требует внимания».

### Ограничения (честно)

- Источник отдаёт измерения на ГРАНИЦАХ окон/сегментов отчётов, а не каждое
  сообщение трекера: подсегментные изменения между измерениями Nav.by не показывает.
- При простое машины измерений одометра НЕТ вообще (не «ноль км»); отсутствие
  точек вечером/ночью — норма, а не разрыв связи.
- У снимков портала время измерения в API отсутствует: время координаты и время
  получения показываются отдельно, «временем изменения CAN» не выдаются.
- Точность оконного съёма — целые км (округление источника); сегментные методы —
  float (до 0.001 км).
- `odom_can` физически не подтверждён как шина CAN — в интерфейсе нейтральное
  «одометр»; название блока — по требованию задачи («История CAN-пробега»).
